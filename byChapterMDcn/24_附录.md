## 附：23 模式实现状态总览

本书涉及四种运行时。传统 VBScript 代码在 cscript、AxonASP 传统模式、ASPPY 三套引擎下运行同一份代码；Axon VBScript 代码在 AxonASP 下运行；VB.NET 代码在 .NET 下运行。下表对比传统 VBScript 与 AxonASP 两种语法体系下的实现状态，VB.NET 作为语法完备的对照基准（23 个模式全部地道实现，无需任何妥协）。

| # | 模式 | 地道理由 | AxonASP 强类型版 |

| 7 | 外观 | 组合调用子系统，不依赖继承或接口 | 子系统引用 `As CPU`/`As Memory`/`As HardDrive`，参数 `As Long`/`As String` |
| 12 | 享元 | `Dictionary` 做对象缓存已是最优解 | `TreeType` 字段与 `GetTreeType` 返回值强类型；`m_Types` 因 COM 限制保留 Variant |
| 22 | 备忘录 | `Class` + `Property` 做状态快照已地道 | UDT `EditorMemento` + `As String`/`As Integer`，值拷贝防引用泄漏 |

### 四、VB.NET 对照基准

VB.NET 作为语法完备的 OOP 语言，23 个模式全部地道实现，无任何妥协。上表中的"残留缺陷"在 VB.NET 中均有对应解法：

| 残留缺陷 | VB.NET 解法 |
|---------|------------|
| Private 构造函数（单例） | `Private Sub New()` 编译期强制禁止外部创建 |
| 方法重载/双分派（访问者） | `Overloads` 方法重载 + 运行时类型派发 |

### 五、与 GoF-23 相关的缺失语法点及优先级

以"对 23 个设计模式的地道性是否有帮助"为唯一过滤器，AxonASP 仍缺失的语法点如下：

| 优先级 | 缺失语法点 | 影响的模式 | Go 的做法 | 理由 |
|:---:|---|---|---|---|
| P0 | 代码复用机制（继承或 embedding） | 代理、桥接、组合、责任链、模板方法 | struct embedding | 不影响功能——所有模式已能用接口+组合实现。但手动委托转发导致大量样板代码，Go 的 embedding 直接解决 |
| P1 | 方法重载/双分派 | 仅访问者 | type switch | 范围最窄，但访问者模式确实需要双分派才能地道 |
| P2 | 访问控制修饰符 | 单例、备忘录 | 首字母大小写控制可见性 | 影响面小，单例的 Private 构造函数是唯一刚需 |

> **已解决**：`For Each` 自定义集合迭代（原 P0）已由 AxonASP 实现，迭代器模式完全消失。

### 总结

| 状态 | 传统 VBScript | AxonASP | VB.NET |
|------|:---:|:---:|:---:|
| 传统已地道 | 3 | 3 | 3 |
| 彻底解决 | 0 | 18 | 20 |
| 改善但有残留 | 0 | 2 | 0 |
| **地道实现合计** | **3** | **21** | **23** |

AxonASP 让地道实现的模式从 **3/23** 提升到 **21/23**。18 个"彻底解决"模式通过 `Implements` 接口、`Static` 静态变量、`Event` 事件机制、`For Each` 自定义集合迭代等扩展，实现了编译期类型安全的多态派发与原生遍历，无需辅助类或完整限定名。VB.NET 作为对照基准，23 个模式全部地道实现——这印证了"语法完备性"对设计模式落地的决定性作用。

剩余 2 个模式的残留缺陷，对照 Go 语言来看可分为两类：

- **Go 也没有但有替代方案的**：方法重载/双分派（Go 用 type switch）。AxonASP 当前用接口+手动分支替代，功能等价但样板代码更多。
- **Go 有而 AxonASP 没有的**：访问控制（Go 的首字母大小写）。单例的 Private 构造函数是唯一刚需。

Go 没有"继承"和"方法重载"这两个被广泛认为"OOP 必备"的特性，却依然能地道地实现全部 23 个 GoF 模式。这说明这些特性对设计模式而言并非必需——接口 + 组合才是核心。AxonASP 已具备接口和组合，方向正确。

### 六、本书用到的 AxonASP 新特性

AxonASP 为 VBScript 引入了大量现代化特性，本书只用了其中 8 个。以"对 23 个设计模式的地道性是否有帮助"为过滤器，这 8 个中 4 个是核心，4 个是锦上添花。

**通过 GoF-23 过滤器的（核心）：**

| 特性 | 用在哪里 | 为什么是核心 |
|---|---|---|
| `Implements` 接口 | 17 个模式的多态派发 | 没有它，工厂、代理、适配器、策略等模式只能靠方法名约定，不地道 |
| `Event`/`RaiseEvent`/`WithEvents` | 第14章观察者 | 没有它，观察者只能手动维护数组，不地道 |
| `Static` 静态变量 | 第1章单例 | 没有它，单例只能靠全局变量，破坏封装性 |
| `For Each` 自定义集合迭代 + `[DispId(-4)]` | 第16章迭代器 | 没有它，迭代器需要手写 `HasNext`/`NextItem` 类；有了它，迭代器模式完全消失 |

**未通过 GoF-23 过滤器的（锦上添花）：**

| 特性 | 用在哪里 | 为什么过不了过滤器 | 价值 |
|---|---|---|---|
| 强类型（`As Type`） | 17 个"彻底解决"模式（除迭代器 #16 因依赖内置 Collection COM 对象无法完整标注外）+ 3 个"传统已地道"模式的子系统引用、字段与参数，合计 20 个模式 | 23 个模式用 Variant 都能实现，类型安全不是模式的地道性问题 | 消除整类运行时类型错误，IDE 智能提示的基础 |
| UDT（`Type`） | 第22章备忘录（`EditorMemento`） | 备忘录用 `Class` + `Property` 已地道，UDT 只是更优雅 | 值语义天然防止引用泄漏，减少样板代码 |
| `Enum` 枚举 | 第17章责任链（`LogLevel`） | 可用 `Const` 替代，功能等价 | 可读性提升，IDE 补全支持 |
| `IsNot` 运算符 | 第17章责任链（`m_Next IsNot Nothing`） | `Not x Is Nothing` 功能等价，只是 `IsNot` 更清晰 | 消除 `Not ... Is Nothing` 的优先级歧义，guard clause 更易读 |

没有这 4 个核心特性，23 个模式中 18 个无法地道实现；没有那 4 个锦上添花的特性，23 个模式照样地道——但代码更安全、更简洁、更易维护。其中强类型已覆盖 17 个"彻底解决"模式（迭代器 #16 因依赖内置 Collection COM 对象，`m_Items` 等字段无法标注）与 3 个"传统已地道"模式，合计 20 个；剩余第 16 章迭代器因 COM 互操作限制保留 Variant。这说明"锦上添花"不等于"无足轻重"——它让本就地道的代码更安全、更易维护。未来 AxonASP 若引入更多通用语言改进（如 `AndAlso`/`OrElse` 短路求值、带参构造函数等），同样可以用 GoF-23 过滤器评估其优先级，与此处的分类互不干扰。
